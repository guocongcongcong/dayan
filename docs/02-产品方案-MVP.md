# 产品方案：把大衍筮法做成一个能用的东西

> 前提：流程已经拆清楚了，见 `01-大衍筮法流程.md`
> 本文只回答一个问题：**第一版到底做什么、怎么做、先不做什么。**

---

## 1. 先明确：我们卖的不是"算命"，是"记账 + 查字典"

把原始流程拆开，用户真正花力气的地方是：

| 环节 | 用户付出 | 是否值得保留 |
|---|---|---|
| 摇蓍草（18 变） | 20~40 分钟，很累 | **✅ 保留，这是灵魂** |
| 每一步记数字 | 容易记错、记乱、丢掉 | ❌ 该电子化 |
| 数字 → 卦 | 查表、算、容易错 | ❌ 该电子化 |
| 定本卦 / 变卦 / 动爻 | 容易搞反上下、搞错变爻 | ❌ 该电子化 |
| 查该看哪句辞（7 条规则） | 90% 的人不会 | ❌ 该电子化 |
| 找高岛原文 | 翻书/翻 PDF | ❌ 该电子化 |
| **解卦** | 需要功力 | ⭕ 后期交给 AI |

**结论：第一版 = 「输入数字 → 输出一个结构完整的卦」+「该看的原典一字不差地摆在你面前」。**

不碰"预测吉凶"、不做"AI 大师"、不做社区。先把**确定性部分做到 100% 正确**。

---

## 2. 核心洞察：三种输入，一种输出

现实中每个人记数字的方式都不一样。有人记「每爻剩下的 36/32/28/24」，有人记「每爻最后是 9/8/7/6」，
还有人老老实实记「每变的 5/9、4/8、4/8」。**产品必须三种都吃。**

```
输入 A：每爻直接是 6/7/8/9          ┐
输入 B：每爻三变的挂扐数 5|9,4|8,4|8 ├→ 统一归一化 → 6/7/8/9 → 卦
输入 C：每爻剩余的 36/32/28/24      ┘
```

这一步做对了，产品立刻比"只能自己摇"的 App 好用——**它变成了你纸质记录的电子版**。

---

## 3. MVP 功能边界

### ✅ P0 做（第一版，能发给朋友用）

1. **起卦录入**
   - 六个爻，由下至上（初爻在最下面）
   - 每一爻可选三种输入口径（见上）
   - 实时回显：这一爻是 ○ / -- / — / ×
2. **成卦展示**
   - 本卦（卦名 + 卦符 + 六爻图 + 上下卦）
   - 变卦（同上）
   - 动爻高亮
3. **取辞**
   - 自动判定"看哪句"，并**把判定理由写出来**
     （例：*「两爻动 → 看本卦两动爻，以上爻为主 → 姤九四」*）
   - 展示：卦辞、爻辞、大象
4. **高岛易断原文**
   - 本卦总论
   - 动爻对应的断语（一字不改，标注出处）
   - 变卦总论（若有变）
5. **存证 / 分享**
   - 生成一张竖版卡片图（卦象 + 数字 + 日期 + 问题）
   - 这条直接对应"小红书发帖"的场景

### ❌ P0 不做

- 账号体系、登录
- AI 聊天式解卦（先把原文摆对，再谈解读）
- 铜钱卦 / 梅花易数 / 六爻纳甲 等其他占法
- 社区、案例库、榜单
- 付费

### ⏭ P1 / P2

- **P1**：模拟摇卦（严格按 3/16、5/16、7/16、1/16 权重，过程可见）+ 占例本（记录问题与结果，回看准不准）
- **P2**：AI 解读（RAG）。把高岛原文 + 卦爻辞检索出来喂给模型，要求**必须引用原文**，禁止自由发挥。

> **关于「喂给 AI」这件事，先说清楚：不要微调，要用 RAG。**
>
> | | 微调（fine-tune） | RAG（检索增强） |
> |---|---|---|
> | 做法 | 把 20 万字喂进去改模型权重 | 原文切块建索引，问的时候检索出来塞进上下文 |
> | 原文保真 | ❌ 会记串、会改写 | ✅ 一字不差 |
> | 更新内容 | 每次都要重训 | 改数据即可 |
> | 成本 | 高 | 几乎为零 |
>
> 解卦这个场景，用户要的是**"高岛原话怎么说"**，不是"模型觉得怎么说"。
> 所以正确姿势是：**检索负责事实，模型只负责把原文讲成人话。**
> 20.7 万字的语料，一次检索几段塞进上下文完全放得下，微调纯属自找麻烦。

## 4. 技术方案

### 形态：单页静态站

```
dayan-iching/
├── index.html          # 全部 UI + 逻辑，零构建
├── data/iching64.json  # 64 卦：卦名/卦符/爻辞/高岛原文（205 KB，已备好）
└── lib/
    ├── engine.js       # 数字 → 爻 → 卦 → 取辞（纯函数，可单测）
    └── render.js       # 画卦
```

**为什么不上框架：** 零依赖、零后端、双击就能开、扔到 GitHub Pages / Vercel 就有公网链接。
数据 205 KB，一次加载完，断网也能用。这是"简单产品"的最短路径。

### 核心引擎（真正要写对的部分，约 120 行）

```js
// 1. 归一化：三种输入 → 6/7/8/9
normalize(input) -> [6|7|8|9] × 6

// 2. 成卦：6/7/8/9 → 本卦、变卦
cast(lines) -> { primary, changed, moving: [1..6] }
//   本卦阴阳： 9、7 → 阳(1)     8、6 → 阴(0)
//   变卦阴阳： 9→阴  6→阳  7、8 不变

// 3. 卦 ID：由上下卦数字拼成，如乾上巽下 = "15"（与数据文件同构）
hexId(binary) -> "15"

// 4. 取辞：按朱熹七条
selectTexts(primary, changed, moving) -> [{卦, 爻, 依据}]

// 5. 模拟：按真实权重随机
simulate() // 9:3/16  7:5/16  8:7/16  6:1/16
```

> **第 3 步的坑**：数据文件以 `(上卦, 下卦)` 为键，顺序是**上卦在前**。
> 而爻序是**初爻在前（下卦在前）**。这两套顺序混了就是经典 bug，必须写单测锁死。

### 数据：已经准备好了

`data/iching64.json` —— 64 卦，每卦含：

```json
{
  "id": "15",
  "binary": [0,1,1,1,1,1],          // 初爻→上爻，1=阳
  "upper": {"num":1,"name":"乾","symbol":"☰"},
  "lower": {"num":5,"name":"巽","symbol":"☴"},
  "name": "天风姤", "symbol": "䷫",
  "judgement": "女壮，勿用取女。",   // 卦辞
  "image": "天下有风，姤；后以施命诰四方。",  // 大象
  "lines": {"1":"初六：系于金柅…", …},        // 爻辞
  "takashima": {
    "general": "【占】得此卦者…",              // 高岛总论
    "lines": {"1":"断曰：…", …}                // 高岛逐爻断
  }
}
```

**校验结果：64 卦齐全，无缺漏，20.7 万字，高岛总论 + 六爻断语全部到位。**

### 还需补的数据

- [ ] **文王卦序**（第 1~64 卦编号）—— 目前缺，需补一张 64 条映射表
- [ ] 每卦的「卦德 / 上下卦关系」一句话（可选，用于展示）

## 7. 风险与要提前想清楚的事

### ① 版权（最需要你拍板）

- 高岛吞象原书（1884，日文）已进入公有领域。
- 但市面流通的中文译本是**现代译本**（黄敦兵译 / 孙正治译等），受著作权保护。
- 我拿到的这份 GitHub 数据**没有 license**，属于"能用但来源不明确"。

**处理建议：**
- 自己/朋友用 → 直接用，没问题。
- 要公开上线 → 三选一：
  a. 换公有领域的文言底本
  b. 自己重译关键段落（工作量大）
  c. 联系出版方拿授权

### ② AI 幻觉 = 这个产品最大的雷

解卦最怕 AI 编造原文。P0 阶段**坚决不上 AI**，只做检索展示。
P2 上 AI 时，强制"先检索、后生成、必须引用"，并保留原文对照。

### ③ 仪式感 vs 便利

电子化最大的风险是把它变成"抽卡游戏"。
设计上：**主路径是"你真摇了，来录数字"**，模拟摇卦放次要位置，且过程要能看到蓍草的增删。
这不是玄学洁癖——用户流失的核心原因是"感觉不郑重"，不是"不够快"。

### ④ 顺序 bug

上下卦 vs 初上爻的顺序，是这个项目最容易出错的地方。必须单测。
