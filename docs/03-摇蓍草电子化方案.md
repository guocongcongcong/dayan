# 方案：把摇蓍草电子化成一个按钮

> 结论先说：**能做，而且能做得比"随机出个卦"诚实得多。**
> 原型已在 `index.html`，双击就能用。

---

## 1. 一个必须先拍板的技术决策

「摇蓍草电子化」有两条路，90% 的同类产品走了下面这条偷懒的路：

| | A. 结果级（多数做法） | B. 过程级（本方案） |
|---|---|---|
| 做法 | 直接从 6/7/8/9 里按 3:5:7:1 抽一个 | 真跑 18 变：分二/挂一/揲四/归奇 |
| 中间数字 | **编不出来** | 真摇出来的，5/9、4/8 对得上 |
| 能不能展示过程 | 不能，一展开就露馅 | 能，18 变逐行摊开 |
| 分布正确性 | 靠人写权重，改错就错 | 由算法推导，天然正确 |
| 代码量 | 10 行 | 40 行 |

**选 B。** 理由只有一个但很硬：

> 卦的结果本身没人能验证对错，但**过程可以被验证**。
> 一旦用户点开"十八变明细"，A 方案的每一行数字都是假的——而算卦这件事，最不能假的就是过程。

这不是玄学洁癖。你能把「这一卦怎么来的」摊开给人看，产品才有底气。

## 2. 算法（40 行，逐变真模拟）

```
一变(n 根):
    左 = 随机 1..n-1           // 分二，随手分两堆
    右 = n - 左
    右 -= 1                    // 挂一，从右堆取一根夹指缝
    余左 = 左 % 4 || 4         // 揲四，整除时按 4 计
    余右 = 右 % 4 || 4
    拿掉 = 1 + 余左 + 余右      // 归奇
    返回 拿掉

一爻:
    n = 49                     // 大衍之数五十，其用四十有九
    重复 3 次: n -= 一变(n)
    得 n/4                     // 36→9 32→8 28→7 24→6

一卦:
    重复 6 次 一爻()           // 初爻在前，上爻在后
```

- 一变只能拿 **5 或 9**，二三变只能拿 **4 或 8** —— 这是算法自然的结果，不需要特判
- 三变后剩余必为 **36/32/28/24**，除以 4 得 9/8/7/6
- 9/7 为阳、8/6 为阴 → 本卦；9→阴、6→阳 → 变卦

## 3. 随机源：别用 Math.random

| 做法 | 问题 |
|---|---|
| `Math.random()` | 可预测、可按种子复现，且实现有偏 |
| `randomInt(4)` 直接取 0-3 | **取模偏差**，1/2/3 概率略高于 0 |
| ✅ `crypto.getRandomValues` + 拒绝采样 | 无偏、不可预测 |

```js
const limit = Math.floor(4294967296 / max) * max;
let x; do { crypto.getRandomValues(buf); x = buf[0]; } while (x >= limit);
return x % max;
```

> 电子化的唯一实质变化就是：**随机性从"手"换成了"密码学随机数"**。
> 这是整个方案里唯一动到本质的地方，其它全是记账。

## 4. 实测校验（我跑过了）

### 4.1 结构自洽（12 万次）

| 检查项 | 结果 |
|---|---|
| 一变取值 | 只有 {5, 9} ✅ |
| 二变 / 三变取值 | 只有 {4, 8} ✅ |
| 剩余总数 | 只有 {36, 32, 28, 24} ✅ |
| `49 − (三变之和) = 剩余` | 5 万次全通过 ✅ |

### 4.2 分布

| 爻 | 理论 | 保真模式实测 | 经典模式实测 |
|---|---|---|---|
| 9 老阳 | 18.75% | **19.72%** | 18.85% |
| 7 少阳 | 31.25% | 30.30% | 31.18% |
| 8 少阴 | 43.75% | 44.11% | 43.64% |
| 6 老阴 | 6.25% | **5.87%** | 6.33% |

### 4.3 为什么保真模式有约 1pp 偏差（重要，不是 bug）

保真模式里，「去 4 根」和「去 8 根」理论上各占 1/2，实测是 **51.1% : 48.9%**。原因很具体：

> 二变从 44 根开始，左堆只能取 1..43 —— **43 个分点分给 4 个余数类，除不尽**。
> 余数 1/2/3 各 11 种分法，余数 0 只有 10 种，于是「去 4」略占便宜。
> 后果就是**老阳偏高、老阴偏低，各约 1 个百分点**。

这不是实现错误，是**物理模拟的真实结果**。朱熹那组 3:5:7:1 是理想化的数理值。

所以引擎做了两个模式（页面底部可切）：

| 模式 | 含义 | 适合 |
|---|---|---|
| **保真推演**（默认） | 逐变真模拟，中间数字全是真的 | 想看得见过程、想晒十八变 |
| **经典概率** | 严格按 3:5:7:1，再补一组自洽的三变 | 只认朱熹数理、要理论精确 |

> 两边的卦名、卦符、变卦完全一样，只是概率的"哲学"不同。

## 5. 交互：一个按钮，0.6 秒

```
┌──────────────────────┐
│        大 衍          │
│  大衍之数五十·十八变   │
│                      │
│      ( 摇 卦 )        │   ← 唯一的按钮
│                      │
└──────────────────────┘
        ↓ 点击
   第 一 变 → 第 十八 变   （进度条，约 610ms）
        ↓
┌──────────────────────┐
│  本卦 ䷫ 天风姤 → 变卦 ䷴ 风山渐 │
│  ┌─┐ ┌─┐  ┌─┐ ┌─┐          │
│  │─│ │─│  │ │ │ │  （六爻图，  │
│  │ │ │─│  │ │ │─│    动爻高亮）│
│  初 二 三 四 五 上           │
│  8  9  7  9  7  7           │
│  动爻：二、四  ○老阳 ○老阳    │
│                              │
│ [再摇一次] [十八变明细] [复制] │
└──────────────────────┘
```

设计上的取舍：

- **不要"点一下立刻蹦出来"** —— 610ms 的推演过程是唯一的仪式感残渣，去掉就真成抽卡了
- **数字必须显示**：8 9 7 9 7 7，这是用户能抄进本子、能核对、能发帖的东西
- **十八变明细可展开**：每爻三变的数字 + 剩余数 + 定爻结果，这是"过程可信"的证据
- **复制**：直接生成可发小红书的纯文本

## 6. 数据结构

```js
{
  lines:  [8, 9, 7, 9, 7, 7],              // 初爻 → 上爻
  steps:  [[5,4,4],[5,8,8],[9,8,4],…],     // 每爻三变收走的根数
  moving: [2, 4],                          // 动爻位置（1=初爻）
  primary: { name:'天风姤', symbol:'䷫', id:'15' },
  changed: { name:'风山渐', symbol:'䷴', id:'57' },
  mode:   'true'
}
```

有 `steps` 就够复现整个卦了，不需要存别的。

## 8. 已知限制

1. **`file://` 打开时复制走的是 execCommand 兜底**，部分浏览器可能失败（会弹框给出全文）。
   挂到公网（https）就自动走 `navigator.clipboard`。
2. 没有历史记录。每次刷新就没了 —— 这是 P1 的「占例本」。
3. 没有分享图，只有可复制的纯文本。生成竖版卡片图要额外做 Canvas 渲染。
4. **不做解卦**（按你说的）。语料在，随时能接上。
